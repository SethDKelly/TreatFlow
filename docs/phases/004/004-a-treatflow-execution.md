## 2. Adversarial modularity method

For each candidate and competing decomposition, document:
1. **Specificity:** can part of its behavior be desired independently; are unrelated purposes bundled, or is it a fragment rather than a coherent user function?
2. **Minimum completeness:** remove one essential action; can the purpose/OP still be fulfilled? If not, where must the behavior live?
3. **Intrinsic independence:** conceptually remove all peer concepts; is its purpose, state and end-to-end behavior still intelligible? Distinguish an abstract eligible object supplied by the environment from another concept's private state.
4. **Genericity:** do arbitrary substitutions of abstract identity tokens leave behavior unchanged? Preserve genuine semantics of units, monitored time, corrections, authority and disclosure.
5. **Boundary alternatives:** retain, split, combine, reframe, generalize, reduce, expand, reject; document a concrete counterexample and reasoned disposition **without arbitrary numeric scoring**.

Compare concept-facing behavioral value, not document size, action count, implementation ease, persistence design or service boundaries. Independence does not mean no eventual product interaction. Phase 005 owns authoritative synchronizations; Phase 006 extrinsic application inclusion/dependence; Phase 008 broader reuse review.
